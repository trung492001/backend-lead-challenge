## 3. Part A — Implement the deposit → wager → withdrawal flow (~3h)

### A1. Create a deposit — `POST /deposits`

Request:
```json
{ "memberId": "<uuid>", "amount": "100.50", "turnoverMultiplier": 1 }
```
- Creates a **funding transaction** in `Pending` state, returns `201` with the transaction `id` and a `pspRef` (generated by me — the mock PSP echoes this ref back in the callback).
- **No money moves at this step.**
- `amount`: decimal string, must be positive.
- `turnoverMultiplier`: integer ≥ 0, default `1` (used in A4).

### A2. Handle the PSP callback — `POST /psp/callbacks`

Request:
```json
{ "pspRef": "<ref>", "status": "completed", "amount": "100.50" }
```
`status` ∈ `completed | failed`.

Must assume (this is the hard part, the main thing being graded):
- **The same callback can be redelivered** (retries, sometimes minutes/hours late).
- **Two deliveries of the same callback can arrive concurrently** (two requests running in parallel at the same time) → must guard against a race condition.
- The callback's `amount` may differ from the deposit's `amount` → **I have to decide how to handle it and document why in `DECISIONS.md`** (e.g. trust the original amount, trust the callback's, or reject on mismatch).
- The callback may reference an unknown `pspRef` → must handle it (no crash, a sensible error).

Hard requirements:
- A `completed` deposit must credit the wallet **exactly once**, no matter how many times the callback is redelivered or how concurrently.
- **Every balance change must write an append-only ledger entry** (`wallet_txs` table, or another name of my own design) so that the wallet balance is **always reconstructible from the ledger** (the ledger is the source of truth, not the plain `balance` column).
- The funding transaction must go through an **explicit state machine**: `Pending → Completed / Failed`. Invalid transitions must be **rejected explicitly**, never silently applied (e.g. no `Completed → Pending`, no double `Completed`).

### A3. Record a wager — `POST /wallets/:walletId/wagers`

Request:
```json
{ "amount": "10.00" }
```
- Debit the wallet (**reject if insufficient balance**).
- Accrue **turnover** (see A4).
- Must write a ledger entry.
- **Same concurrency requirement as A2**: two concurrent wagers **must not** overdraw the wallet.

### A4. Withdrawal + turnover lock — `POST /withdrawals`

Request:
```json
{ "memberId": "<uuid>", "amount": "50.00" }
```

Business rule (a real anti-abuse control, not a rule drawn up for fun):
- Each **completed** deposit adds a turnover requirement = `amount × turnoverMultiplier`.
- Each wager adds to accrued turnover = the wager's `amount`.
- A member may only withdraw when **accrued turnover ≥ total required turnover**.
- If not enough: return **`422`** with a body stating **how much turnover is still outstanding**.
- If valid: **debit immediately**, create a funding transaction in `Pending` state (assume a human approves it later — **no need to build the approval flow**).

### A5. Required tests (minimum)

- Duplicate callback (sequential, not concurrent) → does **not** double-credit.
- **Concurrent** duplicate callback → does **not** double-credit. (This is the hardest test, and demonstrates race-condition handling.)
- Concurrent wagers → do **not** overdraw the wallet.
- Turnover lock: blocks withdrawal when turnover is insufficient, and allows it once sufficient (test both directions).
